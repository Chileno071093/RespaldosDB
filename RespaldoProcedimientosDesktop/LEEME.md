# Respaldo de objetos SQL

Proyecto VB.NET Windows Forms para Visual Studio 2022 y .NET Framework 4.8.

El proyecto usa el formato SDK de .NET (sigue siendo Windows Forms sobre .NET Framework 4.8) y el paquete NuGet `Microsoft.Data.SqlClient`, que se restaura al compilar. Se compila desde Visual Studio o con `dotnet build RespaldoProcedimientosDesktop\RespaldoProcedimientosDesktop.vbproj`; el ejecutable queda en `bin\Debug\` (o `bin\Release\` con `-c Release`).

Abra `RespaldoProcedimientosDesktop.sln` en Visual Studio. Complete servidor, usuario y password de SQL Server y pulse **Elegir bases...**: la aplicación se conecta a `master` y abre una lista con casillas de las bases de usuario en línea a las que ese login tiene acceso (no incluye `master`, `model`, `msdb` ni `tempdb`). Marque una o varias; el filtro y los botones **Marcar visibles** / **Desmarcar visibles** ayudan con listas largas. También puede escribir los nombres en el campo **Bases de datos**, separados por coma o punto y coma. Si vuelve a abrir la lista y acepta el mismo conjunto de bases, se conserva la vista previa.

La columna **Cambios** de la vista previa compara cada script con la definición actual en SQL Server (con las mismas reglas que **Comparar**): **Iguales** si la liberación no cambia el objeto, o `-N +M` con las líneas que quita y agrega (en rojo). Si el objeto está declarado en varios archivos con cuerpos distintos, se indica "(varia por archivo)". El resumen muestra cuántas filas listas tienen cambios.

Con varias bases, **Analizar** revisa los scripts en cada una: la vista previa tiene una fila por objeto y base, con la columna **Base**. Si una base no responde (por ejemplo, por falta de permisos), sus filas quedan como **Base no disponible** y el resto continúa; si no responde ninguna, se muestra el error. Al respaldar, si los objetos marcados son de una sola base, la carpeta tiene la estructura de siempre; si son de varias, se crea una subcarpeta por base (`<Base>\Procedimientos`, `<Base>\Vistas`, ...), y cada archivo lleva su propio `USE [base]`.

Elija la carpeta con los archivos `.sql` y la carpeta donde desea guardar el respaldo. Pulse **Analizar** para ver los objetos antes de crear archivos. Marque los que desea guardar y pulse **Respaldar seleccionados**. El botón **Comparar** muestra la definición actual junto con la declaración del archivo y una comparación por líneas (algoritmo de Myers, el mismo de `git diff`), con números de línea, eliminaciones en rojo y agregados en verde. Por defecto oculta los tramos iguales y deja 3 líneas de contexto; **Mostrar el objeto completo** los despliega. La comparación ignora los comentarios previos al `CREATE` (SQL Server los guarda en la definición), la diferencia entre `CREATE`, `ALTER` y `CREATE OR ALTER` (SQL Server guarda un `ALTER` como `CREATE`), las mayúsculas y `PROC`/`PROCEDURE` del encabezado, y los espacios al final de línea. **Ignorar diferencias de espacios y tabulaciones** también ignora cambios de indentación. **Cancelar** detiene la operación activa de análisis, búsqueda o respaldo; si ya terminó, el botón queda deshabilitado. Durante el respaldo se escriben primero archivos temporales, que se limpian si se cancela antes de crear la carpeta final.

La aplicación recuerda servidor, bases de datos, usuario, carpetas y opciones entre sesiones; se guardan al analizar y al cerrar la ventana en `%APPDATA%\RespaldoObjetosSQL\configuracion.xml`. El password nunca se guarda. Para volver a los valores iniciales, borre ese archivo.

El usuario y el password se envían con `SqlCredential` (el password como `SecureString`), no dentro de la cadena de conexión, y se liberan al terminar cada operación. **Cifrar conexion** (activada por defecto) exige cifrado TLS. **Confiar en el certificado del servidor** (activada por defecto) acepta certificados autofirmados, habituales en servidores internos: la conexión va cifrada, pero no se valida la identidad del servidor. Si el servidor tiene un certificado válido, desmarque esa opción para validarlo.

Para ubicar objetos en otras bases del mismo servidor, seleccione una o varias filas de la vista previa con Ctrl/Shift y pulse **Buscar en bases**. La búsqueda revisa las bases de usuario en línea y accesibles para el login SQL. Muestra base, tipo, esquema y nombre; seleccione una o varias filas del resultado y pulse **Agregar bases seleccionadas** para sumarlas a las bases de análisis. Esta consulta no cambia ni respalda las otras bases. Los catálogos solo muestran los objetos para los que el usuario tiene visibilidad, por lo que la ausencia de una coincidencia no demuestra que el objeto no exista.

Durante **Buscar en bases**, la aplicación muestra la base que está revisando y el avance (por ejemplo, 3/20). El resultado muestra el tiempo de cada base y los errores de las bases omitidas. Pulse **Cancelar** para detener el recorrido; si hay una consulta en curso, solicita su cancelación. La conexión tiene un límite de espera configurado en 5 segundos y cada consulta de búsqueda, en 10 segundos, por lo que la cancelación puede tardar un poco en reflejarse. Si la versión anterior de la aplicación se queda detenida, cierre la ventana y abra la solución actualizada en Visual Studio.

La aplicación lee el contenido de cada archivo `.sql` y reconoce declaraciones `CREATE`, `ALTER`, `CREATE OR ALTER` y `DROP` de procedimientos, vistas, funciones, triggers (de tabla o vista, de base de datos y de servidor `ON ALL SERVER`) y sinónimos.

- **`DROP`**: si la liberación elimina un objeto, aparece con Cambios **Se elimina**; se respalda su definición actual y el script de reversión lo vuelve a crear (sin sus permisos). Si el mismo script lo elimina y lo vuelve a crear (`IF OBJECT_ID(...) IS NOT NULL DROP ...` + `CREATE ...`), se trata como una modificación y el detalle avisa que se pierden sus permisos (`GRANT`).
- **Triggers de servidor**: aparecen con la base **(servidor)**, se respaldan en la carpeta `Servidor` (con `USE [master]`) y tienen su propio `Restaurar_servidor.sql`. Para verlos, el login necesita el permiso `VIEW ANY DEFINITION`.
- **Sinónimos**: se respaldan en `Sinonimos`; como no admiten `ALTER`, el script de reversión los elimina y los vuelve a crear apuntando al objeto original.
- **Sentencias sin reversión**: lo que la liberación hace fuera de esos objetos (tablas, índices, tipos y otros cambios de estructura; `INSERT`/`UPDATE`/`DELETE`/`MERGE`/`TRUNCATE`; `GRANT`/`REVOKE`/`DENY`, usuarios y roles; `sp_rename`; `ENABLE`/`DISABLE TRIGGER`) se lista al analizar y en `Sentencias_sin_reversion.txt` dentro del respaldo, y el script de reversión lo advierte al inicio. El respaldo no puede deshacer esas sentencias; para eso hace falta, por ejemplo, un `BACKUP DATABASE`. Lo que está dentro del cuerpo de un procedimiento o trigger no cuenta, y las tablas temporales (`#tabla`) se ignoran.
 Usa el nombre declarado dentro del SQL, sin depender del nombre del archivo. Luego consulta en la base indicada sólo las definiciones de los nombres detectados; antes de respaldar vuelve a consultar sólo los nombres seleccionados. La opción **Incluir subcarpetas** permite buscar también en `Interfaz` al seleccionar la carpeta principal. Los archivos se leen respetando su BOM (UTF-8, UTF-16, UTF-32); si no tienen BOM se intenta UTF-8 y, si no es válido, se usa la codificación ANSI de Windows (por ejemplo, Windows-1252), de modo que la `ñ` y los acentos se conservan. Si el mismo objeto está declarado en más de un archivo, la columna **Archivo** muestra `(+N)`, el detalle enumera los otros archivos y **Comparar** agrega una pestaña de diferencias por cada archivo.

Durante **Buscar en bases** se usa una sola conexión y se cambia de base con `ChangeDatabase`, en lugar de abrir una conexión (y un login) por cada base.

Antes de escribir, la aplicación vuelve a consultar SQL Server y detiene el respaldo si alguna definición seleccionada cambió desde la vista previa. También comprueba que no hayan cambiado los archivos `.sql` de los objetos seleccionados (incluidos los archivos duplicados); los cambios en otros archivos no bloquean el respaldo. Cada ejecución crea una carpeta con fecha y hora dentro del destino, con subcarpetas `Procedimientos`, `Vistas`, `Triggers` y `Funciones`. Cada archivo respaldado termina en `_<nombre de la base>.sql`, por ejemplo `[Reporte].[P_Ejemplo]_AdministradorEmpleado_PEMSACELAYA.sql`. Los archivos `.sql` y los reportes `.txt` se guardan en UTF-16 LE con BOM y saltos de línea CRLF. Se agrega un `.editorconfig` que configura tabulaciones para los `.sql` en editores compatibles; la indentación del cuerpo de cada objeto se conserva tal como la devuelve SQL Server. `Declaraciones_detectadas.txt` muestra qué objeto se leyó de cada archivo. `Objetos_no_respaldados.txt` muestra los omitidos por estado o selección. `Archivos_sin_objetos.txt` enumera archivos sin declaraciones reconocidas. `Verificacion.txt` registra los archivos SQL verificados y su SHA-256. La aplicación no ejecuta los scripts de origen ni modifica objetos en SQL Server.

El respaldo admite rutas de más de 260 caracteres (por ejemplo, destino largo + subcarpeta por base + nombres de objeto largos) aunque Windows no tenga activadas las rutas largas. Si alguna ruta final supera ese límite, la aplicación lo avisa al terminar, porque el Explorador o SSMS podrían no abrir esos archivos; en ese caso conviene elegir una carpeta destino más corta.

Cada respaldo incluye además un script de reversión por base, `Restaurar_<base>.sql` (en la raíz del respaldo, o en la subcarpeta de la base si se respaldaron varias). Ejecutarlo completo en SSMS devuelve todos los objetos respaldados a su definición: los que existen se modifican con `ALTER`, por lo que conservan sus permisos (`GRANT`); los que la liberación haya borrado se recrean (primero un esqueleto mínimo y luego el `ALTER`; los triggers, con su definición completa). Respeta `ANSI_NULLS` y `QUOTED_IDENTIFIER` de cada objeto, aplica el orden funciones, vistas, procedimientos, triggers, y se puede ejecutar más de una vez. No elimina objetos que la liberación haya creado y que no estaban en el respaldo.

Cuando un objeto no aparece en el catálogo con el usuario usado, la aplicación muestra **No visible o inexistente**: esas situaciones no se pueden distinguir de forma fiable con esas mismas credenciales. Si el catálogo muestra el objeto pero no entrega su definición, se informa por separado como **Sin definicion**.

## Pruebas

El proyecto `Pruebas\RespaldoProcedimientosDesktop.Tests.vbproj` (MSTest, incluido en la solución) tiene pruebas unitarias (codificación, parser, comparación, script de reversión, configuración) y de integración contra SQL Server LocalDB: análisis y respaldo de una y varias bases, verificación previa al respaldo, búsqueda en bases, la ventana principal manejada con sus botones y la ejecución real del script de reversión después de simular una liberación. Las pruebas de integración crean bases y un login SQL temporales en `(localdb)\MSSQLLocalDB` y los borran al terminar; si LocalDB no está instalado, se marcan como no concluyentes.

Para ejecutarlas: desde el Explorador de pruebas de Visual Studio, o con

```
powershell -ExecutionPolicy Bypass -File Pruebas\Ejecutar-Pruebas.ps1
```

o directamente con `dotnet test Pruebas\RespaldoProcedimientosDesktop.Tests.vbproj` (`-Filtro "Name~Respaldar"` en el script, o `--filter` en `dotnet test`, ejecuta solo algunas).

Todo se probó contra LocalDB; falta probarlo en el servidor real.
